# Limitations

darwin-wasm is a research prototype. It runs **small, statically-behaving
ARM64 Mach-O user programs** inside a browser tab. It does **not** run iOS
apps, and it is not an iOS emulator. Please read this before filing "X does
not work" issues.

## What will not run

| You drop… | What happens | Why |
|---|---|---|
| An `.ipa` / `.app` bundle | rejected: not a Mach-O | Only a single `MH_EXECUTE` Mach-O file is accepted. |
| A universal (fat) binary | rejected: `FAT_MAGIC` | Thin it first (`lipo -thin arm64`). |
| An `x86_64` or `arm64_32` slice | rejected: wrong `cputype` | Only `CPU_TYPE_ARM64` (0x0100000c). |
| A binary linked with Xcode 13+/iOS 15+ (`LC_DYLD_CHAINED_FIXUPS`) | rejected with `UnsupportedMachO: LC_DYLD_CHAINED_FIXUPS … not supported yet` | Only the classic `LC_DYLD_INFO_ONLY` opcode format is parsed. Chained fixups are the obvious next step for the mini-dyld. |
| Anything importing UIKit, Foundation, CoreFoundation, libobjc, Swift runtime, … | loads, but every import is bound to `0` and listed as *unresolved*; the first call faults at address `0` | No dyld shared cache, no frameworks, no Objective-C/Swift runtime exist in the browser. Only the ~20 libc/libSystem functions in `hostcalls.ts` are provided. |
| arm64e binaries | fault at the first `PACIBSP`/`RETAB` | Pointer authentication instructions are not implemented. |
| Anything using floating point or NEON | fault with `UnsupportedInstruction` | The interpreter is integer-only. Even `printf("%f")` inside a real libc would fail, but our host `printf` runs in TypeScript. |
| Encrypted (`LC_ENCRYPTION_INFO_64` with `cryptid=1`) or code-signature-enforced binaries | rejected | darwin-wasm never decrypts or verifies anything; App Store binaries are encrypted. |
| Multi-threaded programs | `bsdthread_create` returns `ENOTSUP` | Single hart, single thread; exclusives always succeed. |
| Programs that read files, sockets, or the environment | `EBADF` / `ENOSYS` / empty results | No filesystem, no network, `envp` is empty unless supplied by the UI. |

## Faithfulness caveats

* **Memory model**: sparse 64 KiB pages, no permission enforcement beyond the
  mapped/unmapped distinction (writes to `__TEXT` succeed). `__PAGEZERO` is
  unmapped, so null dereferences do fault.
* **Syscall semantics** are minimal stand-ins (see
  `SUPPORTED_INSTRUCTIONS.md`), not an XNU reimplementation. `mach_msg`
  never delivers a message. `sysctl`/`proc_info` are unsupported.
* **Timing**: `CNTVCT_EL0` returns the instruction count, not a clock;
  `gettimeofday` returns the browser's wall clock.
* **Performance**: BigInt-based interpreter, a few million instructions per
  second depending on the browser. Fine for demos, unusable for anything
  interactive beyond the canvas sample. A Rust → WebAssembly backend is the
  documented path (`ARCHITECTURE.md`), not implemented.
* **Framebuffer** is a fixed 320×240 RGBA buffer presented on demand via an
  extension syscall; there is no display server, IOKit or Metal.
* **Input** is a queue of mouse/touch events the guest must poll; no
  keyboard, no HID descriptors.
* **Stack**: argv/envp are laid out per the Darwin ABI but the `apple[]`
  vector is empty and there is no `_dyld_start`, so binaries that expect
  `dyld` to have run initialisers (`__mod_init_func`, Objective-C `+load`)
  will misbehave.

## Browser sandbox

Everything runs client-side inside the page's JavaScript sandbox:

* No files leave the browser; uploaded binaries are parsed in memory only.
* No `SharedArrayBuffer`, workers or WASM threads are required.
* The site is a static GitHub Pages deployment (`/darwin-wasm/`), so there
  is no backend to talk to and nothing is logged server-side.
* Emulated code cannot escape: the guest only ever touches the `Memory`
  object and the explicit syscall surface.

## Legal

darwin-wasm ships **no Apple code, firmware, dyld shared cache or system
libraries**. All sample binaries are generated by `tools/gen-fixtures.ts`
from hand-written assembly. You are responsible for the binaries you load.
